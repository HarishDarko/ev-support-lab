# 0001. Transaction-aware reconciliation

Status: accepted (lab). Revised after review: stricter policy (Decision 4 to 6); revised again after a second review: ongoing is not a flag, completeness is counted from the Started, per-EVSE serialization (Decision 2, 5, 6, 7); revised a third time: the flag is checked again under the locks, and "newer" is the backend's receipt order (Decision 6, 7, 8).

## Context

A charger sees the driver unplug and sends `TransactionEvent(Updated, EVCommunicationLost)`. Within about 90 s the websocket drops (close 1006, no close frame). The charger reconnects, sends `StatusNotification(Available)` and replays its queued `TransactionEvent(Ended, offline=true)` with the original timestamp. Some firmware sends the Ended after the Available; some drops the queue and never sends it.

The legacy backend treats an Ended that arrives while the EVSE is Available as out of order and ignores it, and nothing else closes a transaction. The transaction stays `Charging`, idle fees accrue, and the EVSE shows "in use" downstream. A support runbook (close the session, reverse the fees) clears the symptom each time but not the cause.

## Decision

Behind a per-station flag (`station.fix_enabled`, default `lab.fix.enabled`):

1. Apply events by `(station, transactionId, seqNo)` in seqNo order (ADR 0002). A late Ended for an open transaction is applied whatever the EVSE status says.
2. When a station opens a new websocket session while the backend holds an open transaction on it, ask the charger with `GetTransactionStatus`. `messagesInQueue=true` means wait, up to a limit. `ongoingIndicator=true` means the transaction is active: leave it open and do nothing, with or without `messagesInQueue=true` (an active transaction can have undelivered events, so the combination is valid, not contradictory). No review flag is raised for that.
3. If the charger reports nothing pending and no Ended arrives within a grace period (default 60 s, injected `Clock`), treat the Ended as lost and close the transaction provisionally at its own last meter value and timestamp (ADR 0003).
4. Reconcile only on an explicit `ongoingIndicator=false` together with `messagesInQueue=false`. An omitted indicator is not `false`: it goes to a person (`ONGOING_NOT_REPORTED`).
5. Reconcile only when the data supports "stopped": no gap in the transaction's own seqNo sequence (`SEQUENCE_GAP`; a transaction with no Started has nothing to count from and goes to a person as `STARTED_NOT_RECEIVED`), at least two meter samples that agree within epsilon, at least a minimum spacing apart (`SAMPLES_TOO_CLOSE`), and a last sample that is neither older than a staleness bound (`METER_STALE`) nor dated more than a clock-skew allowance ahead of the backend (`METER_IN_FUTURE`). Thresholds and their reasons are documented on `ReconciliationPolicy.Settings`. The sequence starts at the lowest seqNo of the transaction's Started, not at 0: OCPP 2.0.1 allows a charger to keep one ever-increasing counter.
6. Do not touch a transaction when a newer one has started on the same EVSE. "Newer" is the order in which the backend received the Starteds (`transaction.started_received_at`, the backend's injected `Clock`, read after the EVSE lock is taken), not the charger's start timestamps: receipt order is monotonic per EVSE under the lock, and the charger clock is not, because it can be corrected backwards between two transactions. A transaction with no Started received has no `started_received_at`, is never counted as newer, and goes to a person as `STARTED_NOT_RECEIVED`, as before. Apart from the "ongoing" wait and the "not yet" waits, every case above leaves the transaction open with a review reason.
7. Serialize per EVSE. "No newer transaction" is only true if nothing can start one between the check and the close, and a lock on the old transaction's row does not stop an insert of a new one. The reconciliation decision and the handling of a `Started` therefore take a per-EVSE advisory lock (`pg_advisory_xact_lock(hashtext(station), evseId)`, `EvseStatusRepository.lockEvse`) before anything else. It is an advisory lock rather than a lock on the `evse_status` row because a Started can arrive before any StatusNotification, when there is no row to lock. **Lock order, everywhere: EVSE lock first, then the transaction row.** Nothing asks for the EVSE lock while holding a transaction row, and no database transaction holds two EVSE locks, so the order cannot cycle. The sweeper lists a candidate with the EVSE it saw, takes that EVSE's lock, locks the row, and skips the candidate if the row has since moved to another EVSE (the next sweep lists it again). The sweeper also skips any station whose flag is off at that moment.
8. The flag is read twice: when the sweeper lists a candidate, and again once the EVSE lock and the transaction row are held, immediately before the decision. The wait for the locks can be long, and a flag turned off during it must count. **Turning the flag off stops any reconciliation that has not yet been decided; it does not undo ones already made.** A sweep that finds the flag off at the second look takes no action: no closure and no review flag. Provisional closes already made stay, and a late Ended still adjusts them (ADR 0003).

The decision is a pure function (`ReconciliationPolicy`) of the transaction, the time and one fact about the EVSE. A sweeper (scheduled in production, called by hand in tests) applies it.

## Consequences

- The bug no longer needs a person in the common case. The cost is one extra round trip per open transaction per reconnect.
- The policy prefers leaving a session open over closing one that might still be delivering. It does not close a session whose recorded energy was still rising or whose charger reports it ongoing. It cannot see energy it was not told about: a charger that keeps delivering while it reports flat samples and `ongoingIndicator=false` would be closed. A closure is a judgement on the data held.
- Chargers that omit `ongoingIndicator`, sample faster than the minimum spacing, share one seqNo counter between concurrent transactions, or stamp meter samples ahead of the backend's clock will reach a person. That is the intended direction of error; if it is too many, tune the settings per firmware rather than loosening the rule.
- A session the charger keeps reporting ongoing stays open and unflagged. There is deliberately no timeout to a person: the answer is a snapshot taken at the reconnect, the next reconnect asks again (and replaces it), and long sessions are legitimate, so a timeout would flag healthy ones. Finding a session that has been open unusually long, with no further reconnect, is general session monitoring and out of scope for this reconciliation.
- A flagged transaction is not "stuck" in our metric because someone has been asked, but it is still open until that person acts.
- Old transactions on a station that reconnects after the flag is turned on are evaluated too. Most are flagged (a newer transaction exists).
- With the flag off the legacy path runs unchanged, so the bug stays reproducible.
